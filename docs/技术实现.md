# 技术实现

## 一、为什么不直接改上游源码重编译

上游是 Kotlin + Gradle/Loom 工程。要在没有可用构建环境的情况下（`maven.fabricmc.net` 在部分网络下不可达）
为 10 个平台各出一份产物，最短路径不是重建整个工程，而是：

> **保留上游已编译好的 jar（含它自己那套版本适配），只替换"音乐数据来源"这一层的类。**

这一层（`NeteaseApi` / `NeteaseLogin` / `NeteaseTrack` / `NeteasePlaylist` / `LyricsProvider`，
以及一起听用的 `party/Firebase`）基本不碰 Minecraft 的渲染与 API，只做 HTTP + 数据变换，
所以可以脱离具体 MC 版本单独实现。

代价是：**替换类必须与调用方的内部签名完全一致**（JVM 链接是按名字+描述符匹配的）。
这也是本仓库对每个平台分别编译的原因——见第三节。

## 二、管线

```
上游 jar (v1.5.0 + <平台>)
      │
      ├─[1] 用该 jar 自身当 classpath 编译 src/main/java 里的替换类（--release 8，与上游字节码目标一致）
      │
      ├─[2] 逐条目重写 jar：
      │       · 同名 class  → 用新编译的替换
      │       · 新出现的内部类（如 NeteaseLogin$Reply、Firebase$1） → 追加
      │       · 被取代后成为孤儿的类 → 删除（NeteaseTrack$Companion 等 3 个）
      │       · 界面文案常量 → 二进制常量池精确替换
      │       · fabric.mod.json / mods.toml / neoforge.mods.toml → 版本号与描述
      │
      └─[3] 逐类结构校验 + 全 jar 内部引用校验（与上游基线对比）
```

## 三、为什么每个平台单独编译

1. **签名**：`DangoMusic.Companion.getInstance().getClientDir()` 这类调用在不同版本里描述符可能变化；
   编译期报错是最硬的信号。
2. **新增/删除接口**：上游 1.5.0 的 UI 层可能调用了旧版没有的方法；用目标 jar 编译+链接校验能立刻发现。
3. **字节码目标**：上游全部是 Java 8 字节码（major 52）。替换类也必须 `--release 8`，
   否则 1.20.1 那些跑在 Java 17 的客户端会 `UnsupportedClassVersionError`。

## 四、常量池改写为什么不能 `bytes.replace()`

class 文件的常量池里，UTF8 项是「tag + 2 字节长度 + 内容」。直接替换文本会让长度字段与实际不符，
或让常量池计数（`long`/`double` 占两个槽位）错位，结果就是游戏启动即
`ArrayIndexOutOfBoundsException: readBootstrapMethodsAttribute`。

正确做法（`tools/qqpatch.py`）：

1. 按格式遍历常量池，得到每个条目的原始字节；
2. 逐条重写：命中替换表的 UTF8 项重新编码并写新的长度，其余原样拷贝；
3. **常量池计数原样抄**，不重算；
4. 最后用 `validate_class()` 走完整结构：接口表、字段、方法、属性，偏移必须正好等于文件长度。

替换只用于界面文案这种「值变了但类型/结构不变」的场景；改逻辑一律通过换 class 实现。

## 五、校验方法（`tools/verify_all.py`）

| 检查 | 手段 | 目的 |
| --- | --- | --- |
| 结构完整 | `AsmVerify`（ASM 逐类 parseField/parseMethod） | 常量池或属性写坏会立刻失败 |
| 内部引用 | `LinkCheck` 收集所有 `me/sorihiko/dango/**` 的方法/字段引用，沿父类链解析 | 替换后不能有悬空引用 |
| 基线对比 | 同一检查跑上游原始 jar，取**差集** | 上游自身就有的噪音不算问题，只看"新增" |
| 文案 | 读常量池断言新文案存在、旧文案消失 | 防止某平台字符串没命中 |
| 元数据 | 断言 `version=1.5.1-qqmusic`、loader 版本范围未被破坏 | 防止 `bytes.replace` 误伤 |

`LinkCheck` 的基线对比很关键：上游 jar 本身就有约 190 条"解析不了"的成员引用
（Kotlin 编译产物里对 `Object.getClass()`、接口默认方法、以及跨 jar 类型的引用），
如果只看绝对值会误报，看差集才是有效信号。

## 六、QQ 音乐接口要点

- **搜索/详情/歌词/播放地址**都走 `https://u.y.qq.com/cgi-bin/musicu.fcg`（POST，JSON）。
- **播放地址**：`M800`（320k MP3）优先，需要登录态；未登录只能拿到试听片段。
- **登录态**：`qqmusic_key` / `qm_keyst`（101 字符，`Q_H_L_...`），存 `config/dangomusic/qqmusic_cookie.txt`，
  有效期约 3 天。
- **扫码登录链**（`tools` 之外的实现细节，见 `NeteaseLogin.java`）：
  1. `ptqrshow` 取二维码与 `qrsig`
  2. `ptqrlogin` 轮询：`66`=未扫，`67`=已扫待确认，`65`=已过期，`0`=成功
  3. `check_sig` 换 `p_skey`
  4. 走 `graph.qq.com/oauth2.0/authorize` 拿 `code`（`g_tk` 用 `p_skey` 算 hash33，种子必须是 `5381`，
     并带 `openapi=1010_1030`）
  5. `musicu.fcg` 的 `QQConnectLogin.LoginServer/QQLogin`，参数**只有** `{"code": ...}`
     （带 `appid` 或 `refresh_token` 会返回 `10006`）
  6. 得到 `musickey` / `musicid` / `refresh_token`（`keyExpiresIn=259200` 秒）

## 七、一起听协议要点（`party/Firebase.java`）

- 匿名登录：`accounts:signUp`，token 缓存到 `config/dangomusic/firebase_auth.json`，过期用 refreshToken 续。
- 房间：`rooms/<5 位码>`，字符集 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`（去掉易混字符）。
- 时钟对齐：`PUT clock/<uid>` 写 `{".sv":"timestamp"}`，用返回值算与本地的偏移，之后所有时间戳都按服务器算。
- 冲突控制：读取带 `X-Firebase-ETag`，写入用 `if-match`，实现 CAS。
- 同步：`listen()` 每 `pollMs`（默认 3000 ms）拉一次房间快照；房主 1.5 s 心跳、15 s 全量；跟随端容差 700/1500 ms。
- 房间回收：`ABANDONED_MS = 660000`（11 分钟无心跳）。

**坑**：`HttpURLConnection` 不支持 `PATCH`（会抛 `ProtocolException: Invalid HTTP method: PATCH`），
所以 `patch()` 实际发 `POST` + `X-HTTP-Method-Override: PATCH`。
上游原版也有这个隐患，这里一并修掉了。

## 八、踩过的坑（给后来者）

| 现象 | 原因 |
| --- | --- |
| 游戏启动 `ArrayIndexOutOfBoundsException` 于 `readBootstrapMethodsAttribute` | 常量池计数被重算错了 |
| 编译通过但游戏里 `NoSuchMethodError` | 换的类与调用方描述符不一致（没按目标 jar 编译） |
| 按 M 没反应 | 把模块名 `NeteaseMusic` 改了，`config.json` 的 `enabled` 失效 |
| 登录按钮点了没反应、也读不到登录态 | `qqmusic_cookie.txt` 是 0 字节（只复制到剪贴板没粘进文件） |
| 一起听建房失败 | 国内直连 Firebase 域名超时；需要代理且必须真正走通 |
| 房主能切歌、成员不跟 | 成员端 `pollMs` 太大或时钟偏移过大，先看日志里的 `clock offset` |
